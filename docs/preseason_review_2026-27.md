### 2026-10-01 — 賽季復盤（v2）

**做了什麼**：用 git 歷史重建 4/10–6/13 每場比賽的賽前快照並評分（`scripts/audit_live_record.py`）；用前一天數據表重建 2024-25／2025-26 資料集，拿正式模型重新評分（`scripts/audit_feature_leak.py`）。重建的洩漏版資料集與正式 `dataset.sqlite` 重疊的 1,862 列逐欄完全相同，驗證了比對方式。

**發現**：
1. 同日數據洩漏：2025-26 的 TeamData 有 497/536、AdvancedTeamData 有 486/528 張「當天表」已含當天比賽。去除洩漏後，2025-26 value+過濾從 24-2（92.3%）降到 **24-9（72.7%）**，ML 從 70.4% 降到 **66.8%**。
2. 實戰賽前紀錄（n=119）：ML 48-30（61.5%）、季後賽 GOLD+SILVER 每場主訊號 32-27（54.2%）、大小分 46.2%。
3. 有 44 條賽前顯示的訊號在賽後從檔案中消失（15 中、29 錯），追蹤器的 67.6% 因此被灌水。
4. 選表 bug：`odds_2025-26`（殘缺，562 場）在 `MAX(Date)` 同日時勝出，dataset 少約 760 場；總決賽期間的球隊輪廓只用 43 場歷史計算。
5. 值得保留：主場 value 注無洩漏兩季 16-4；10–11 月 value 注 28-12，12–1 月只有 14-14；ML 模型在 70–80% 信心區間偏保守（預測 74%、實際 83%）。

**決定**：6/23 回顧的 85%／86.7%／67.6% 全部作廢，改以第 8 節的定義衡量（賽前凍結紀錄 ≥30 注且 ≥85% 才算達標）。記憶檔中的相關宣稱已更正。首頁賽季儀表板上方加上稽核後的真實數字（過渡版），舊卡片暫留但已標明作廢。

**注意順序**：P0 選表修正若單獨上線，`season_stats` 會以完整賽季但仍含洩漏的特徵重算（value+過濾會變成 24-2、92.3%），首頁數字反而更誇大。所以選表修正與洩漏修正要一起上線，再重算 `season_stats`。

**下一步（10/2）**：P0 選表邏輯統一＋洩漏修正（同一批上線）→ 重建 dataset → 確認 2025-26 約 1,320 場、`audit_feature_leak.py` 第 1 部分對新 dataset 為零 → 重算 `season_stats`。另外追蹤 Duren 的 qualifying offer 結果。

**新發現**
1. **第五個根因：首頁的 ATS 卡片評的不是實戰那個模型。** `SeasonStats` 把 60 個滾動近況欄位照原順序接上去（199 欄），模型只收 175 欄 → 預測丟例外 → 靜默退回「完全不餵近況特徵」的版本。實戰（`main.py`）則是把後加的欄位排到最後再截斷。舊的 85.0% 因此是「洩漏 × 殘缺賽季 × 少了 36 個特徵的模型」三者疊加。已改成和實戰相同的欄位順序，並拿掉靜默 fallback；欄位規則集中到 `AdvancedFeatures.ats_model_columns`（`main.py` 兩處與稽核腳本共用，實戰預測輸出逐場比對不變）。
2. **今天 06:00 的 pipeline 失敗了**（`Export_JSON`：`no such table: 2026-27`）。賽季標籤 10/1 就換成 2026-27，但該賽季的賠率表要到 10/20 才會出現；不修的話會連續失敗到開幕。已修：`_update_playoff_quarters` 改用共用 loader；匯出改用 `_reporting_season`（新賽季還沒有比賽時，沿用最近一個有資料的賽季，所以首頁、H2H、dates.json 在開幕前維持 2025-26）。
3. **`patch_scores.py` 把表名寫死成 `"2025-26"`**：新賽季的比分永遠不會被補上，結果、休息天數、近況特徵全部會斷。已改成依日期取當季表（表還不存在時沿用上一季）。`update_odds.py` 在表不存在時也會直接報錯，已加防呆。
4. `series_state_2025-26` 從總決賽前後就是壞的（只剩 4 列）——同一個選表 bug。2023-24 也補回 1 場（MIN 4-0 PHX）。
